Part IThe idea

Everything in this repository follows from one dissatisfaction: a JEPA's predictor is designed by a person, and there is no reason to believe the shape a person chose matches the shape of the problem.

Start with the thing being extended. A Joint Embedding Predictive Architecture learns by hiding part of an input, encoding what remains, and predicting what the hidden part would encode to. Not what it looks like — what it encodes to. There is no decoder anywhere in this codebase and no pixel ever gets reconstructed.

That choice is the foundation everything else sits on, so it is worth being precise about why it is made.

Why predict embeddings instead of pixels?

Because most of the detail in a pixel is unpredictable and worthless. Reconstruct a hidden patch of grass and the model must commit to the exact position of every blade. It cannot know them, so it spends capacity learning to hedge — producing blurry averages — and the gradient signal that shaped that capacity taught it nothing about grass.

Predicting in latent space lets the target itself decide what is worth representing. If blade positions are not encoded, they are not predicted, and no capacity is spent on them. The model is graded on the abstraction rather than on the rendering.

The cost of that choice is that the target is no longer fixed. In pixel reconstruction the answer key is the input; it cannot be gamed. In latent prediction the answer key is produced by a network that is also learning, and there is a trivial way to score perfectly: both encoders agree to output the same constant for every input. Loss zero, information zero. This is representation collapse, and preventing it drives several of the design decisions in Part II.

Now the dissatisfaction. In a standard JEPA the predictor is a transformer of a chosen depth and width. Someone picked those numbers. The architecture is fixed before training begins and never changes, no matter what the data turns out to look like.

Why should that bother anyone?

Because the predictor is where the model's theory of the data lives, and a fixed architecture asserts that theory in advance. If the data has periodic structure, a stack of attention blocks can approximate periodicity — but nothing in it is shaped like a cycle, and it must spend capacity discovering that shape from scratch every time.

The proposal in this repository is that the model should notice such structure in its own behaviour and build a predictor to match. Not adjust weights within a fixed shape — add new shapes.

Which raises the question the whole architecture is an answer to: where would the model look to find out what shapes it needs? It cannot look at the data — it has no labels, and the data is exactly what it does not yet understand. The answer this codebase gives is that it should look at its own uncertainty. Specifically: at the geometry of the regions where its predictions are least determined.

That answer decomposes into three problems, and those three problems are the three systems. Find the uncertain regions. Move through them and record the path. Measure the shape of the paths and build something matching that shape. Each system solves one, hands its product to the next, and the last hands its product back to the first.

Read that figure once more with the cadences in mind. Exploration does not run every step and crystallization does not run every exploration. Part VIII explains why those rates differ; for now the point is that the loop is not a tight cycle but three processes on three clocks, and the slowest one is the one that changes the architecture.

Part IIThe substrate

Before anything self-organizes there is an ordinary JEPA, and almost every detail of it is a defence against the collapse problem from Part I.

Four components. A context encoder s_θ that sees a few visible blocks. A predictor p_φ handed those encodings plus positional placeholders for the hidden blocks. A target encoder s_ξ that encodes the hidden blocks to produce the answer. And a loss between prediction and answer.

E(x, y) = ‖ s_θ(x) − s_ξ(y) ‖² E_pred(x, y) = ‖ p_φ(s_θ(x)) − sg[ s_ξ(y) ] ‖² sg = stop-gradient ξ ← m·ξ + (1−m)·θ m: 0.996 → 1.0

The third line is the anti-collapse mechanism. The target encoder is not trained. It is a copy of the context encoder whose parameters are dragged along by exponential moving average, and gradients are blocked from entering it twice over — once by torch.no_grad() and again by an explicit .detach().

Why an EMA copy rather than a second trained encoder?

Collapse requires both encoders to agree to degenerate together. If the target is trained, that agreement is reachable by gradient descent — it is a genuine minimum and the optimizer will find it.

An EMA target cannot participate. It only ever moves toward where the context encoder already was, with a lag of roughly 1/(1−m) steps. At m = 0.996 that is a 250-step lag. The context encoder is therefore always predicting a slightly stale version of itself, and a constant output would have to be a fixed point of that lagged dynamic — reachable in principle, but the optimizer gets no gradient pointing toward it, because the target does not move in response to the context encoder's attempt to make it move.

The momentum schedule runs from 0.996 up to 1.0 across training. Early on the target should track a rapidly improving encoder; late on it should be nearly frozen so the objective stops moving underneath the optimizer.

Three shape facts in that figure explain most of the code you will read later.

First, masking happens after positional embeddings are added. The surviving tokens still know where on the image they came from. Without that, the predictor's positional mask tokens would be meaningless — it would be told to predict "position 34" without any of its inputs knowing where position 34 is relative to them.

Second, masks are index tensors, not booleans, and applying one concatenates along the batch dimension rather than zeroing entries in place.

Why gather-and-concatenate rather than a boolean mask?

Because the blocks have different sizes and there are several of them per image. A boolean mask keeps the tensor at full length and forces the encoder to process tokens it will discard — wasted compute on 90% of the sequence.

Gathering produces a short sequence containing only real tokens. Stacking four different context blocks along the batch axis instead of the token axis then lets the encoder treat them as four independent short sequences, which is what they are — four separate views of the same image. The cost is that batch size silently multiplies by nenc, and every downstream shape has to account for it.

Third, the predictor is narrower than the encoder: 96 dimensions against 192, projecting back up at the end.

Why bottleneck the predictor?

Because a predictor with as much capacity as the encoder can memorise instead of predict. Given enough width it can learn an idiosyncratic lookup from context patterns to target patterns without either representation becoming meaningful.

Squeezing it forces pressure back onto the encoder. If the predictor cannot represent the mapping, the only way to reduce the loss is for the encoder to produce targets that are actually predictable from context — which is the representation you wanted.

Why one shared mask token rather than one per position?

Because the token must carry no information about what it is standing in for. A single learned vector, identical everywhere, plus a positional embedding, tells the predictor exactly one thing: where to predict. Per-position tokens would give it a second channel it could learn to exploit, and the task would quietly become easier than intended.

The loss

Why smooth L1 rather than plain MSE?

Smooth L1 is quadratic near zero and linear beyond it. Latent targets are moving — the EMA encoder shifts every step — so occasional large residuals are normal rather than a sign of a bad prediction. Under MSE those residuals dominate the gradient and drag the model toward whichever targets happened to drift most that step. The linear tail bounds their influence.

The comparison the repository cares about is with I-JEPA, which uses the same loss; matching it keeps the baseline honest.

The target encoder's unusual safety net

Why bother? Nothing should ever produce NaN here.

Because the target encoder is the one component that gradient descent cannot repair. Corrupt the context encoder and the next few steps push it back toward something sane. Corrupt the target encoder and every subsequent target is NaN, every loss is NaN, and training is over — silently, with no error, until someone reads the logs.

The asymmetry justifies the extra pass. This same reasoning is why the training loop in Part IX has a whole separate skip path that protects the EMA and nothing else.

Part IIIThe mask is the task

Nothing else in the config file changes what the model learns as directly. The mask defines the question; the architecture only answers it.

Masks are generated in the dataloader's collate function, not in the model. One call produces a single large target block covering 20–40% of the patch grid, and four small context blocks covering 15–20% each, sampled from the complement of the target so the two never overlap.

Why blocks, rather than scattered individual patches?

Because scattered patches make the task too easy in an uninteresting way. A single hidden patch surrounded by visible ones can be filled in by local interpolation — the model learns texture continuation, which is genuine but shallow.

A contiguous block removes the local context entirely. To predict its centre the model must use information from elsewhere in the image, which means it must have learned something about what the image is, not just how its textures flow.

Why four context masks against one target?

Two reasons, one conceptual and one about cost. Conceptually, four different partial views predicting the same target teaches the encoder that the target is inferable from many directions — a stronger constraint than a single view provides.

Practically, the target encoder pass is expensive and its result can be reused. Encoding the target once and predicting it from four contexts costs one target pass and four cheap context passes, rather than four of each. That is why the target is repeated with h.repeat(len(masks_enc), 1, 1) rather than recomputed.

Why is the same mask geometry shared across every image in the batch?

So the tensors stack. Per-image masks would produce ragged index tensors requiring padding and a validity mask through every downstream operation. Sharing geometry within a batch and resampling between batches gets nearly the same diversity over an epoch at none of that complexity.

The visible consequence is in the collator: every mask in a batch is trimmed to the smallest one found, so a batch's blocks are equal-length even when the sampler produced slightly different sizes.

Why does the sampler have a timeout and a relaxation step?

Because the constraint can be unsatisfiable. Asking for a context block of a given size drawn entirely from the complement of a large target block, on a small grid, sometimes has no solution. A naive rejection sampler loops forever and the training run hangs with no error.

After twenty failed attempts the sampler drops one constraint from acceptable_regions and tries again, logging as it goes. It degrades the mask quality rather than the run.

Part IVSplitting into three

The division into three systems is not organisational tidiness. It is what makes the same code run on images and on a four-million-edge graph without modification.

System 1 has the least interesting job and the most structurally important one. It is the adapter. It does exactly two things: it instruments the encoder so representation flow is observable, and it manufactures the energy function that System 2 will walk over.

Why hand out a closure instead of a reference to the model?

This is the single decision that graph mode depends on. System 2's Langevin sampler, blank space detector and Fisher metric all accept a bare callable mapping [B,D] → [B]. None of them imports a model class. None of them can tell what kind of data it is exploring.

The consequence is in Part X: swapping the vision encoder for a graph encoder required writing a new encoder, a new masking scheme and a new dataset — and changing nothing at all in the exploration or crystallization code. Had System 2 been written against a model object, that transfer would have been a rewrite.

The broadcasting rule at lines 78–83 exists because of a shape mismatch that shows up immediately in practice. System 2 subsamples up to 256 latent points from a flattened [B·N, D] tensor, which is almost never equal to the target batch size. Rather than constrain the caller, the closure tiles its captured target to match whatever it is handed.

Why pre-allocate the statistics list instead of appending to it?

Because appending resizes, and resizing is not atomic. Under DDP — or any situation with overlapping forward passes — two hooks appending concurrently produce a list of the wrong length, with entries attributed to the wrong layers. The failure is silent and the resulting statistics are quietly wrong.

A fixed-length list written by index cannot exhibit that. Each hook assigns to a slot that already exists. Worst case under concurrency is that a slot holds the newer of two passes, which is fine — these are diagnostics, not gradients.

Why the layering is the way it is

Why put topology at the bottom of the stack?

Because persistent homology genuinely does not need to know anything else. It consumes a point cloud and produces a persistence diagram. Placing it at layer zero, with no internal imports, makes that independence structural rather than a matter of discipline — the layering enforces it, and a future change that made the topology code aware of transformers would show up as a new import in a file that has none.

Part VExploring instead of descending

Gradient descent finds a point. Topology needs a cloud. That mismatch is the reason System 2 exists at all.

System 2 asks a question no ordinary training loop asks: where on this energy surface is the model uncertain? It then deliberately walks there and records the path.

Blank space H(z) = ∇²_z E(z), blank(z) ⟺ λ_min(H) < τ ∨ Var[p(z+ε)] > τ_v Langevin z_{t+1} = z_t − η ∇_z E(z_t) + √(2η/β) · ε_t, ε ~ N(0, I) Temperature β(z) = β₀ / (1 + blank_score(z)) Fisher metric F(z) = (1/σ²) Jᵀ J, J = ∂p/∂z by finite differences
Why a Langevin walk rather than plain gradient descent?

Because descent converges to a point, and a point has no topology. Run gradient descent from a hundred starting positions on a smooth landscape and you get a hundred nearly-identical endpoints. There is nothing there for persistent homology to measure — no loops, no voids, no structure at all.

Adding calibrated noise turns the descent into a diffusion that samples from the energy distribution rather than minimising it. The walker lingers in low-energy basins, occasionally escapes them, and traces out the shape of the region it can reach. That traced shape is the signal. Without the noise term, System 3 would have nothing to work with.

Why turn the noise up where the model is uncertain?

Because those are the regions where new structure might be. A region the model already predicts confidently has nothing to teach it — walking there produces trajectories that trace out shapes the predictor already handles. The interesting geometry is where the model has no opinion.

So the same score that flags a region as blank is fed directly into the temperature map: β = β₀ / (1 + blank_score). High blank score, low β, large noise term, wider steps. Detection and exploration are not two stages — they are one mechanism with the output of the first wired into the second.

Detecting blankness

Two independent signals, OR-ed together. The Hessian route probes curvature: for each of 32 random unit directions, a three-point stencil estimates the directional second derivative. If the smallest curvature found is near zero, the surface is locally flat. The perturbation route jitters the input ten times and measures the variance of the predictor's output.

Why two signals instead of one?

They catch different failures. Flat curvature means the model has no preference — many nearby latents produce the same energy, so it is not committing to anything. High output variance means the model is unstable — small input changes produce large output changes, so it is committing, but inconsistently.

A region can be either without being the other, and both are reasons to go look. They are combined with OR for detection and summed for the temperature score.

Why finite differences rather than autograd for the Hessian?

Two reasons. Cost: exact second derivatives through a transformer are expensive and the probe runs on up to 256 points per cycle. And correctness of assumption: the energy function is supplied by the caller and may not be twice differentiable, or differentiable at all. A finite difference stencil only requires that you can evaluate it.

That is why the whole detector runs under @torch.no_grad() — it never needs a graph. It costs 2 × 32 energy evaluations per point, which is also why exploration is capped at 256 points regardless of batch size.

The walk itself

Why four failure guards around a gradient?

Because the energy function is caller-supplied and the sampler has no way to validate it in advance. Each guard corresponds to a real way an arbitrary callable can fail: it can return non-finite values, it can be non-differentiable and raise, it can be differentiable but disconnected from its input and return None, and it can return NaN gradients.

All four paths return a zero gradient rather than raising. The walk then degrades to pure diffusion for that step — still producing a trajectory, still usable by System 3 — instead of killing a training run that was otherwise healthy. The alternative, letting exploration crash the run, trades a diagnostic subsystem for the whole job.

Two smaller decisions in the same file. Line 62 re-enables gradients inside a @torch.no_grad() context, because sample_trajectory is decorated but the gradient helper genuinely needs a graph. And line 121 clamps the noise scale at 10: a near-zero temperature otherwise produces an unbounded jump that throws the walker somewhere meaningless.

The differentiable variant

A second pathway exists for end-to-end training. differentiable_sample runs a number of detached warm-up steps to get somewhere interesting cheaply, then a handful of steps with create_graph=True so gradients flow back through the exploration itself.

Why warm up detached and only differentiate the last few steps?

Because keeping the graph is what costs memory, and the early steps are the least informative. The first ten steps mostly transport the walker from wherever it started to the region it will explore; gradients through that transport tell you little. The last five steps are where it is actually sampling the region of interest, and those are the ones worth attaching to the loss.

Fisher information, and why there is a third signal

Why a Riemannian metric on top of two existing uncertainty signals?

Because Euclidean distance in latent space is not the distance the model experiences. Two latents a fixed distance apart may produce nearly identical predictions in one region and wildly different ones in another. The Fisher metric measures that: it is the sensitivity of the predictor's output to movement, which is the geometry that actually matters for exploration.

In practice the code uses only its trace, reported as mean_fisher_trace — a scalar per point, high where the predictor is sensitive and low where it is not. It is a diagnostic rather than a driver: the temperature map is built from the blank-space score alone. The full metric machinery is present and tested but the loop does not yet steer with it.

Recording the paths

Why throw away the time ordering?

Because persistent homology does not use it, and pretending otherwise would be misleading. A trajectory arrives as [T, B, D] and is immediately flattened to [T·B, D] — a bag of points with no notion of which came first.

This is the right call for what System 3 does. Homology measures the shape of the set of points: whether they form clusters, whether they enclose a loop, whether they surround a void. A loop in the point set means the walker's reachable region has a hole in it, which is a fact about the energy landscape. Whether the walker went round it clockwise is not.

Two caps: at most 1000 points per trajectory, subsampled by linspace so the whole path is represented rather than just its beginning; and at most 100 trajectories, oldest evicted first. Everything is moved to CPU on arrival, which keeps a long run from silently accumulating GPU memory in a buffer nobody is watching.

Part VIMeasuring shape

System 3 takes the cloud of points a random walk left behind, measures its shape, and turns each durable shape into a neural network. This is where the claim from Part I becomes a mechanism.

The instrument is persistent homology. Grow a ball of radius ε around every point and let the balls merge. Watch which topological features appear and disappear as ε grows from zero upward. A feature that survives across a wide range of ε is real structure; one that appears and dies immediately is sampling noise. That survival span is called persistence, and it is the only quantity that decides whether a module gets built.

Why persistent homology rather than clustering?

Two reasons, and the second is the important one.

First, clustering only finds clusters. In homology terms that is H₀ — connected components — and it is one third of what is available. Loops (H₁) and enclosed voids (H₂) are invisible to every clustering algorithm, and they are exactly the structures that indicate something more interesting than "these points are near each other."

Second, and more fundamental: clustering requires you to choose a scale. Pick a distance threshold, or a k, and the answer changes with the choice. Persistent homology refuses the choice — it computes the answer at every scale simultaneously and then reports which features were stable across scales. The noise filter is not a hyperparameter; it falls out of the method.

Computing it

Three backends, tried in order: giotto-tda, then ripser, then a scipy single-linkage fallback.

Why keep an H₀-only fallback that cannot do the interesting part?

Because failing soft is better than failing hard for an optional dependency — but this one has a sharp edge worth knowing about.

Single-linkage clustering genuinely is the H₀ filtration; the fallback is mathematically correct as far as it goes. What it cannot do is loops or voids. So a run without giotto-tda or ripser installed will keep going, log one warning, and never crystallize anything but attractor modules. If you see only mod_attractor_* ids and wonder why no cycles are forming, check the backend before you touch any threshold.

Why subsample to 500 points?

Vietoris–Rips is roughly O(N³). A point cloud from five trajectories can easily be tens of thousands of points, which is the difference between a crystallization step that takes a second and one that takes an hour. The subsample is seeded (RandomState(42)) so the result is reproducible rather than varying run to run.

Deciding what counts

Why a relative threshold rather than an absolute one?

Because latent norms drift during training. Early on, representations are small and all persistence values are small with them; later they grow. An absolute threshold tuned at epoch 5 finds nothing at epoch 50, or everything — and it would need retuning for every dataset and every embedding dimension.

0.3 × max_persistence asks a scale-free question instead: is this feature comparable to the most durable one we found? That question means the same thing whether latents have norm 1 or norm 100.

Why cap at two features per dimension?

Rate limiting. A single crystallization event can otherwise register a dozen modules, all untrained, all immediately influencing the predictor. max_features=2 bounds how fast the module population can grow, which gives the router and the mixing coefficient time to adapt to each new arrival before the next batch shows up.

Turning features into networks

Why these three architectures specifically?

Each one is the natural predictor for the shape that produced it.

An H₀ component means the walk kept returning to a cluster — a basin in the energy landscape with a location. So AttractorModule is a local predictor with a location: a small MLP multiplied by a Gaussian in the distance to the cluster centroid. Far from the centroid the gate closes and the module contributes nothing. The centroid is frozen (it is a measured fact about the landscape, not something to optimise) while the radius of influence is learned (how far the basin's authority extends is not something the persistence diagram tells you).

An H₁ loop means the reachable region has a hole in it — the walk went around something. Periodicity is the natural functional form, so CycleModule projects the input onto eight learned frequencies and takes sines and cosines. It is a Fourier feature layer, chosen because a cycle is what a Fourier basis is for.

An H₂ void means an enclosed cavity — a region with an inside and an outside and a surface between them. So BoundaryModule learns a sigmoid that decides which side of something the input is on, and blends two linear maps accordingly. It is an interface predictor because a void is an interface.

Why stop at three? Why not H₃ and beyond?

Cost and meaning, in that order. Homology dimension k requires enumerating (k+1)-simplices, and the count grows combinatorially — H₃ on 500 points is dramatically more expensive than H₂. And the interpretive story gets thin: it is clear what a predictor shaped like a cluster or a cycle or a boundary should do, and much less clear what one shaped like a three-dimensional cavity in a 192-dimensional space should do. max_homology_dim=2 is where the cost curve and the interpretability curve cross.

Lifecycle

Why can pruning leave the registry over capacity?

Look at line 127: a module younger than pruning_patience is skipped rather than evicted, and the loop moves on. If every module is new, nothing gets pruned and the count stays above max_modules for a few epochs.

That is the intended behaviour. A module's avg_loss after two batches is noise. Evicting on it would systematically favour whichever modules happened to be created during an easy stretch of training, which is not a quality signal at all. Temporarily exceeding the cap is the cheaper mistake.

Part VIILetting the modules back in

A freshly crystallized module is a randomly initialised network being inserted into a model that was converging. Almost every decision in this part is a defence against that.

Crystallized modules are useless until something calls them. DynamicPredictor is the return path that closes the loop — and it applies three independent brakes to the module contribution before it reaches the output.

Why three brakes rather than one?

They control different things, and any one alone leaves a gap.

The scalar α, initialised at 0.05 via a sigmoid on a learned logit, controls how much module influence there is overall. It is the volume knob, and starting it near zero means a new module cannot damage predictions before it has trained.

The per-token gate controls where that influence applies. Modules are specialists — an attractor module is meaningful near its centroid and meaningless elsewhere. A single global scalar cannot express "relevant for these tokens, not those." The gate is a small sigmoid MLP producing one weight per token position.

The LayerNorm controls magnitude. Crystallized modules are initialised independently and nothing constrains their output scale; a module that happens to emit vectors ten times larger than the base prediction would swamp it regardless of α. Normalising the combined mixture makes α's meaning stable — 0.05 means the same thing whatever the modules happen to output.

Why residual, rather than replacing the base prediction?

Because the base predictor is the thing that works. Modules are a hypothesis about extra structure; the residual form means that hypothesis can only ever be an adjustment. If every module is useless, the model can drive α to zero and it has lost nothing.

The clean consequence is at line 119: with an empty registry, forward returns the base prediction untouched. A TCD run that crystallizes nothing is numerically identical to vanilla JEPA — which means the ablation baseline is free and exact rather than approximate.

Why initialise the router's weights to exactly zero?

Because zero weights and zero bias make the softmax exactly uniform. Every module gets identical routing weight on the first forward pass after it is created.

The alternative — random initialisation — would hand new modules an arbitrary preference ordering that has nothing to do with their quality. The router would then have to unlearn that before it could learn anything real. Starting uniform means the first gradient the router receives is the first real information it has about which module is useful.

Why does the base prediction have no try/except when the modules do?

Deliberate asymmetry, and the docstring calls it out. If the base predictor raises, the model is broken and the run should stop loudly — swallowing that would produce a training run that silently learns nothing.

A crystallized module raising is a different situation. It is one speculative component out of several, generated automatically from a topological feature, and the correct response is to skip it with a warning and carry on. Lines 149–150 then recompute the routing weights for the number of modules that actually survived, so the softmax still normalises over the right count.

Why do new module parameters get zero weight decay?

Because an attractor module's centroid and radius encode a measured location in latent space. Decaying them toward zero would erase exactly the information that justified building the module — the optimizer would slowly delete the discovery.

The same applies to the cycle module's learned frequencies. These are not generic weights where shrinkage is a sensible prior; they are parameters with meaning.

Part VIIIThree clocks

The three systems run at three different rates, for three different reasons — and the loop needs a way to know when it has stopped producing new structure.

Why does exploration not run every step?

Cost. One exploration cycle is 2 × 32 energy evaluations per point for the Hessian probe on up to 256 points, plus 20–50 Langevin steps each requiring a gradient. That is comparable to several training steps. Running it every step would roughly halve throughput for a subsystem that only needs to sample the landscape, not track it continuously.

Why does crystallization run even less often, and why the trajectory minimum?

Because persistent homology on a single trajectory is measuring noise. One walk from one set of starting points traces one path; its shape says as much about where it started as about the landscape. Several trajectories from different starting points, pooled, describe the region.

Hence two independent gates. The divisor spaces crystallization out in time; the min_trajectories check ensures there is enough material regardless of how the divisors happen to line up. Figure 10 shows the case where they disagree — the divisor fires at iteration 5 and the guard vetoes it.

Why only the last five trajectories?

get_point_cloud(last_n=5) deliberately ignores older history. The energy landscape is changing as the model trains — a trajectory from thirty iterations ago describes a landscape that no longer exists. Pooling it with recent walks would blur real current structure against stale structure and depress the persistence of both.

Knowing when it is finished

C(t) = |M(t) − M(t−1)| / max(M(t), 1) module formation rate + KL( R(t) ‖ R(t−1) ) representation drift, 50-bin norm histogram + |S(t) − S(t−1)| energy landscape smoothness change converged ⟺ C(t) < ε for k consecutive iterations ε = 0.01, k = 5
Why three terms rather than just counting modules?

Because the module count alone is easy to satisfy for the wrong reason. A system that has hit max_modules stops creating new ones — the first term goes to zero — while the representations underneath are still churning and the landscape is still reshaping. That is not convergence; it is a full registry.

The second term catches it. Representation drift is measured as a KL divergence between histograms of latent norms across consecutive iterations, which detects the encoder still moving even when the architecture has stopped changing. The third term watches the energy landscape's ruggedness. Convergence means all three have settled: the architecture is stable, the representations are stable, and the landscape they define is stable.

Why is the first iteration's divergence hard-coded to 1.0?

Line 76. On the very first call there is no previous histogram to compare against, and the honest answer is undefined. Setting it to zero would be the natural-looking choice and would be a bug: with zero divergence and zero module change, a cold system could satisfy C(t) < ε on its first few iterations and declare convergence before doing anything.

Forcing 1.0 guarantees the first score is far above ε. The cost is that the first entry in the convergence history is not comparable with the rest, which is why the analysis scripts drop it.

Why all-reduce the convergence score under DDP?

Lines 85–88. Each rank computes its score on its own data shard, so scores differ. Without synchronisation, rank 0 could decide the system had converged while rank 3 disagreed — and since convergence gates behaviour, the ranks would diverge in what they did next. Averaging makes it a collective decision.

Part IXKeeping it alive

One training step has four points where it can refuse to do the normal thing. Every one exists because of the asymmetry established in Part II: the EMA target encoder is the component gradient descent cannot repair.

Why do a NaN loss and a loss spike get different treatment?

Because they mean different things.

A NaN or infinite loss means the gradients derived from it are meaningless. There is nothing to be learned from this batch, so the whole step is abandoned: no backward pass, no optimizer step, no EMA update.

A loss spike — more than ten times the hundred-step rolling average — means something quite different. The gradients are real; the batch was just hard. Throwing away a real gradient because it was large is wasteful, and gradient clipping already bounds how far the parameters can move. So the optimizer step proceeds and only the EMA update is skipped.

The reason to protect specifically the EMA is that its update is not clipped and not reversible. A single extreme step pulls the target encoder somewhere it will take hundreds of steps to drift back from — and every target produced in the meantime is degraded.

Why do the LR, weight-decay and momentum schedules advance even on a skipped step?

Because they are indexed against a total step count computed once at startup: num_epochs × steps_per_epoch. If a skipped step also skipped the schedules, they would finish late — the cosine decay would not reach its endpoint, and the momentum schedule would never reach 1.0. Advancing them keeps the schedules synchronised with wall-clock training regardless of how many steps were usable.

Where the loop attaches

Why does the recursive loop run once per epoch rather than per step?

Partly cost, as in Part VIII. But mostly because the thing it measures does not change on a per-step timescale. The energy landscape is defined by the encoder and predictor; after one optimizer step it is essentially the landscape from before. Exploring it again would produce trajectories nearly identical to the last set, and pooling near-duplicates inflates persistence without adding information.

An epoch is a natural interval over which the landscape has genuinely moved. The energy function is rebuilt from the current target encoder each time, so System 2 always explores the present landscape rather than a cached one.

Why track which module ids have already been seen?

Because add_param_group does not deduplicate. Adding the same parameter twice gives it two optimizer states and effectively doubles its learning rate — a subtle bug that would look like instability confined to crystallized modules. The _known_module_ids set makes registration idempotent.

What --tcd actually changes

Why is the registry shared rather than copied?

This one line is what makes the system recursive instead of a one-way pipeline. System 3 writes modules into the registry; the predictor reads modules out of it. They are the same object, so a module registered during crystallization is live in the very next forward pass.

Copy it and you get a pipeline: the crystallizer discovers structure and nothing ever uses it. The whole feedback loop in Figure 1 runs through this single shared reference.

Part XThe same machine on graphs

Graph mode required a new encoder, a new masking scheme and a new dataset — and not one line of change in the exploration or crystallization code. That is the payoff for the interface decision in Part IV.

In graph mode a "token" is an entity sitting at a point on a sphere. Four signals compose into its embedding: a 384-dimensional sentence-transformer fingerprint, an S² position, a tangent-space velocity, and eight structural features summarising its causal neighbourhood.

Why does the identical pipeline transfer at all?

Because of what System 2 and System 3 actually consume. System 2 takes a callable and a tensor of points. System 3 takes an [N, D] array. Neither has any notion of what the dimensions mean.

Persistent homology on a cloud of latents does not care whether those latents came from image patches or from companies in a supply chain. The geometry is the geometry. That is not a lucky coincidence — it is why the interface was defined as a bare callable in the first place, and Part IV flagged this as the decision graph mode would depend on.

Why spherical harmonics instead of the 2-D sincos grid?

Because entities live on a sphere and a 2-D grid encoding has no meaning there. The vision positional encoding assumes a rectangular lattice where "one step right" is well-defined everywhere. On S² it is not, and using the grid encoding would give nearby points on the sphere arbitrarily different codes near the poles and the date line.

The manifold encoding converts to (θ, φ, r) and applies a log-spaced multi-frequency sin/cos basis, so nearby points on the sphere receive similar codes and antipodal points maximally different ones — the property the grid encoding provides on a plane, reconstructed for a sphere.

Why gate the velocity and causal encodings?

Both enter through a learned sigmoid gate. Not every graph has meaningful velocity, and not every graph has meaningful causal structure — a static co-occurrence graph has neither. Adding an uninformative signal unconditionally injects noise into every token.

The gate lets the model shut a channel it cannot use. Since it is learned, the decision is made per-dataset by training rather than per-dataset by a human reading a config file.

Why grow target masks by BFS on the causal graph?

Because this is the graph translation of the block-masking argument from Part III. There, the point of a contiguous block was that it removes local context and forces the model to reason from elsewhere. On a graph, "contiguous" means connected — so the target is a connected subgraph grown by breadth-first search from a seed node.

Masking random scattered nodes would leave every hidden node surrounded by visible neighbours, and the model could interpolate from immediate neighbourhood structure. Masking a connected component forces prediction across a real gap.

Why does the predictor branch on whether the token count is a perfect square?

Because 2-D sincos positional embeddings require a square grid to exist. 64 tokens is 8×8, so the manifold default still gets the frozen sinusoidal embeddings; an arbitrary entity count has no grid interpretation and falls back to learnable embeddings.

This is the only place in the shared code where graph mode is visible at all — everything else was absorbed by writing new encoder, masking and dataset modules.

The 60.8% figure was a single seed at embed_dim=192, depth=6. Re-running at embed_dim=64, depth=2 across two seeds produced essentially nothing. The analysis attributes the gap to capacity: at the smaller size the crystallized modules have no room to contribute.

What does replicate at every scale tested is module formation itself. Four modules formed reliably in both experiments across both seeds, and convergence arrived within one to three epochs of the vanilla run. The mechanism works; its benefit on small image models does not survive a seed sweep.

How much weight should these numbers carry?

Not much, in either direction. The image results are two-seed comparisons at a scale the repository's own analysis calls too small. The graph results are single runs per benchmark with no variance estimate at all.

Read the graph deltas as promising and the 60.8% as a single-seed artifact. The strongest evidence in the repository is not any of these numbers — it is the sixteen semiconductor modules in the previous exhibit, because interpretable structure recovered without labels is hard to produce by accident.

The single most consequential install

Without giotto-tda or ripser, the crystallizer falls back to scipy single-linkage clustering. It logs one warning and keeps running — but two thirds of the module vocabulary become unreachable, and you will only ever see mod_attractor_* ids.

If a run produces no cycle or boundary modules, check the backend before changing any threshold. This is the failure mode most likely to be misdiagnosed as a tuning problem.
